Technically · what HotSpot must be told

HotSpot writes nothing on OutOfMemoryError, logs no GC and tracks no native memory by default. The image adds, all at start-up (so changing them means a restart):

-XX:+HeapDumpOnOutOfMemoryError                 # .hprof on the FIRST VM-thrown OOM of a JVM
-XX:HeapDumpPath=/dumps/java_oom.<start>.hprof   # unique per start: see gotcha 2
-XX:NativeMemoryTracking=summary                 # NMT, the counterpart of NATIVEMEMINFO
-Xlog:gc*:file=/dumps/gc.%t.log:time,uptime,level,tags:filecount=5,filesize=20m

Red Hat's images (registry.access.redhat.com/ubi9/openjdk-21, -25) are current, free to pull, built on UBI 9 and certified for OpenShift; they run as UID 185, so the Containerfile creates /dumps as root before switching to 1001. Oracle's images are its OpenJDK builds (anonymous pull, but frozen: Oracle updates its OpenJDK builds for six months only, so 25 stays at 25.0.2 and 21 at 21.0.2 from January 2024). Oracle JDK (current updates, Oracle licence terms) is the same VM but needs a docker login. Temurin (eclipse-temurin:25-jdk, :21-jdk) is current and pulls anonymously. All HotSpot images must be JDKs, because on-demand heap dumps need jcmd.

Java 17, 21 and 25

Every scenario was run again on Java 21 LTS (Red Hat 21.0.12, the default; Semeru 21.0.12; Oracle OpenJDK 21.0.2; Temurin 21.0.12) and on Java 17 LTS (Red Hat 17.0.16 on UBI 8; Semeru and Temurin 17.0.20; Oracle OpenJDK 17.0.2), with the same limits and flags. The jar is compiled with --release for each. One class differs: FFM is not final on Java 17 and 21, so the native leak allocates with sun.misc.Unsafe there (Scenario D, D2).

Two lessons. First, a configuration that only just fits on one Java version fails on another: a JVM upgrade or downgrade moves the margin, so size with headroom and re-check after every JVM change. Second, JDK 25 writes a heap dump in parallel segments (.hprof.p0, .p1, …) and merges them at the end, JDK 17 and 21 in one pass. In a 2-CPU container the pause grew from 3–9 s to 13.5–55 s for the same heap: give liveness probes room for it.

Scenario G: 80 %, G1, G1ReservePercent=10

A common production setting, run on all twelve variants in 1 GiB: -XX:MaxRAMPercentage=80 -XX:+UseG1GC -XX:G1ReservePercent=10, direct memory uncapped (port x085). The reserve is 10 % of the heap kept free for G1's evacuations, inside the 820 MiB heap: it leaves no extra room outside it. OpenJ9 ignores both G1 flags.

HotSpot gotchas, all reproduced in the lab

  1. java_pid1.hprof is never overwritten. The PID is always 1, so after the first restart every OOM dump fails with "File exists". Put the start time in HeapDumpPath.
  2. First OOM only. Pair the dump flag with -XX:+ExitOnOutOfMemoryError.
  3. Direct-buffer OOMs are never dumped: they are thrown by Java code, and HotSpot has no throw-event agent.
  4. HPROF ≈ the live heap in size and contains values, so treat it as sensitive. jcmd 1 GC.heap_dump -gz=1 measured 7.6 MB in 1.6 s against 385 MB in 8.8 s. It is not available over JMX, so in-app dumps can't compress.
  5. A dump costs ~30 MiB of memory, and live=true runs a full GC that can grow an overcommitted heap. Both killed the guardian mid-dump. Fix: dump without the full GC near the limit, and fire 64 MiB early.
  6. SIGQUIT is not a trigger: use jcmd from outside, which needs a JDK image.
  7. jps/jstat see nothing for a UID with no name (random UIDs on OpenShift): no hsperfdata. Attach-based jcmd still works.
  8. NMT and the GC log are start-up only (the GC log can also be started with jcmd VM.log).
  9. Serial GC in small containers: few full GCs, so the live-set signal arrives late. Choose a collector explicitly.
  10. Diagnosing a container at its limit can kill it. Anything exec'd runs in the container's cgroup: in one run the sh that read memory.events triggered the OOM kill, and jcmd starts a whole second JVM. Capture evidence before the limit; read cgroup files from the node.
