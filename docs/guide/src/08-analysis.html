Tools in action: from evidence to the line of code

The scenarios produced evidence. This part analyses it with the real tools: Eclipse Memory Analyzer, IBM DTFJ, the verbose GC log and javacores. E0

The workbench: a separate analysis stage

analysis/Containerfile
Technically

A separate image, leaklab-analyzer, packages an IBM Semeru 25 JDK (with jdmpview, jcmd and OpenJ9's DTFJ modules), Eclipse MAT 1.17.0 in headless batch mode (ParseHeapDump.sh), and the IBM DTFJ feature, installed with Eclipse's p2 director so MAT can read OpenJ9 PHD and core files. The evidence folder is mounted read-only. Dumps are copied to a scratch area because MAT writes index files next to the dump it parses.

docker compose --profile analysis run --rm \
  -e TARGET=heapdump.sized.20261017.104316.1.phd \
  -e BASELINE=heapdump.sized.20261017.104116.1.phd \
  analyzer /dumps/semeru-25/sized
Like I'm five

You don't study the photo album in the apartment that's on fire. The photos go to a detective's lab across the street. The lab has its own magnifying glasses (MAT), a special lens for OpenJ9's photo format (DTFJ), and plenty of desk space. The photos are only looked at, never changed.

Why a separate stage
  • Memory: parsing needs about 1–1.5× the dump's live heap. Doing it inside a struggling pod would trigger the next OOMKill.
  • Data protection: dumps hold production data. The workbench is the one controlled place where they're opened.
  • Slim runtime: analysis tools never ship in the production image.
  • Repeatability: the same evidence and the same image give the same report every time, ready to attach to an incident.
In the lab · the evidence analysed below

D1 = heap dump right after "Release" (live set ≈ 57 MiB). Then 120 s of HEAP · 40 req/s · 256 KiB · 20 % retained. D2 = second heap dump. The app's own counters at D2: 971 retained SessionContexts holding 254,541,824 bytes. A correct analysis should land on exactly these numbers.

Inventory: what evidence do we have?

01-inventory.txt
Technically

List the heap dumps, javacores and GC logs, newest first, and pick the pair to compare. Both dumps must come from the same JVM, because object counts from two different processes aren't comparable. Javacores are paired by their 1CISTARTTIME (JVM start time) for the same reason.

Before investigating, the detective lays every photo and diary on the table and checks they're from the same apartment and the same week.

VERDICT: heap exhausted — 22 global GCs recovered almost nothing (GC death spiral before OutOfMemoryError)
Technically

The script reads OpenJ9's verbose GC XML, takes the <mem-info> after every gc-end type="global", and reports used = total − free. That is the live set. It also reads maxHeapSize from the log header to judge scale. The verdict distinguishes rising floor (leak), heap exhausted (many global GCs freeing < 5 %: the death spiral just before OOM), slight rise (inconclusive) and flat.

Like I'm five

Read only one column of the cleaner's diary: "how full was the flat right after a full clean?" It went up, then hit the ceiling, and for 22 cleans in a row the cleaner couldn't throw anything away. Then someone emptied the basket, and it started filling again.

Purpose

It confirms the shape before you dig. It's also cheap: the log is always on and needs no pause, so it is the first thing to read in any incident.

Leak Suspects: MAT's first hypothesis

MAT> org.eclipse.mat.api:suspects
Real output (D2)

Shortest Paths To the Accumulation Point
  ConcurrentHashMap$Node[2048] @ 0xd9b7e9f8                    8,200   254,829,864
  \ ConcurrentHashMap @ 0xd9f15260                                64   254,829,928
  .\ class io.leaklab.leak.CustomerSessionCache   System Class   224   254,830,240
Technically

The first call parses the dump: it reads the PHD through DTFJ, purges unreachable objects, builds the object graph, computes the dominator tree and retained sizes, and writes about 12 index files. The report then flags objects or classes whose retained size is a disproportionate share of the heap. It names the accumulation point (where the memory piles up) and the shortest path to it.

Like I'm five

The detective glances at all the photos and says: "My hunch: most of the stuff hangs off one hook, the CustomerSessionCache. And it's all piled into one basket." It's a hunch, not proof yet.

java.lang.Class                              |   7,730 |    1,731,520

Technically

Instances and shallow bytes per class. Arrays of primitives nearly always top this list because they hold the actual data. The histogram shows where the bytes are, never why they are kept.

Like I'm five

Counting boxes by type: "there's a mountain of paper." True, but paper isn't the culprit. You still need to know who keeps it.

E5

Histogram delta: what grew?

MAT> org.eclipse.mat.api:compare -snapshot2=D1
Real output (D2 − D1)
Class (target − baseline)                      Δ objects   Δ shallow bytes
byte[]                                           +2961        +254665512
java.lang.Object[]                                +975            +54552
java.lang.String                                 +1988            +47712
io.leaklab.leak.SessionContext                    +971            +31072
java.util.concurrent.ConcurrentHashMap$Node       +980            +23520
java.time.Instant                                 +971            +23304
java.util.ImmutableCollections$MapN               +971            +23304
Technically

MAT computes both histograms and subtracts them. Look at the proportions, not just the size. 971 contexts, 971 timestamps (createdAt), 971 attribute maps (Map.of), ~971 map nodes, ≈ 2 × 971 strings (request and customer IDs) and ≈ 3 × 971 byte arrays (payload plus the strings' backing arrays). Everything grows in lock-step with one entity, and 971 is exactly the number of retained requests the app reported. The first non-JDK class that grew, SessionContext, becomes the suspect class for the next steps.

Like I'm five

Compare two photos taken two minutes apart. 971 new folders appeared, and each brought exactly one clock, one label set and one bundle of paper. Whatever makes folders is the problem.

Purpose

Growth is the definition of a leak, and this is the most direct measurement of it. It also filters out large but stable things such as caches with bounds, pools and the parachute, which don't appear in the delta at all.

E6

Dominator tree: which objects keep the most alive?

MAT> dominator_tree
Class Name                                               | Shallow Heap | Retained Heap | Percentage
class io.leaklab.leak.CustomerSessionCache @ 0xd9e49a70  |          224 |   254,830,240 |     81.44%
io.leaklab.load.LoadEngine @ 0xd9cf00f8                  |           64 |    25,166,048 |      8.04%
io.leaklab.load.LoadEngine_ClientProxy @ 0xd9e7caf0      |           72 |    25,165,984 |      8.04%
Technically

Top-level entries of the dominator tree, ranked by retained size. The signature of an accumulation point is a tiny shallow size with a huge retained size: 224 bytes keeping 254 MB alive. The second entry, LoadEngine at 24 MiB, is the lab's intentional OOM parachute, a single byte[24 MiB]. It is large but expected, and it did not grow (step E5).

Like I'm five

Find the strings that hold up the most weight. One thin string holds up 81 % of everything. Another holds a big emergency sandbag that's supposed to be there. Knowing which heavy things are meant to be there is half of the skill.

E7

Immediate dominators of byte[]: who owns the bytes?

MAT> immediate_dominators byte[]
Class Name                       | Objects | Dominated Objects | Shallow Heap | Dom. Shallow Heap
io.leaklab.leak.SessionContext   |     971 |             1,942 |       31,072 |       254,572,888
io.leaklab.load.LoadEngine       |       1 |                 2 |           64 |        25,165,880
<ROOT>                           |       1 |            25,848 |            0 |         1,385,312
Technically

For every byte[], MAT finds its nearest dominator and groups the results by the dominator's class. 971 SessionContexts exclusively own 254,572,888 bytes. The app's own counter said 254,541,824 bytes of payload; the extra ~31 KB is the ID strings. Tool and ground truth agree.

Like I'm five

For each pile of paper, ask "whose desk is this on?". Almost all of it sits on 971 identical desks.

OQL: what do the leaking objects look like?

MAT> oql "SELECT …"
MAT> oql "SELECT s, s.@usedHeapSize, s.@retainedHeapSize FROM io.leaklab.leak.SessionContext s"
s                                             | s.@usedHeapSize | s.@retainedHeapSize
io.leaklab.leak.SessionContext [id=0xd9d81940]|              32 |             262,336
io.leaklab.leak.SessionContext [id=0xd9d81978]|              32 |             262,336
Technically

OQL is MAT's SQL over objects, with built-in attributes such as @retainedHeapSize, @usedHeapSize and @GCRootInfo. Each context is 32 bytes itself and retains 262,336 bytes: the 256 KiB payload plus its strings, map and timestamp. Uniform sizes point to one code path. The object ID feeds the next step.

Like I'm five

Ask the photo archive a precise question: "show me every folder and how much it drags along." They're all the same size, so one machine made all of them.

E9

Path to GC roots: why can't the GC free it?

MAT> path2gc 0xd9d81940 -excludes …
Real output: the proof
                                                                 shallow      retained
io.leaklab.leak.SessionContext @ 0xd9d81940                           32       262,336
|-  java.util.concurrent.ConcurrentHashMap$Node @ 0xd9d7c3a0          24       524,864
|  |- [44] java.util.concurrent.ConcurrentHashMap$Node[2048]       8,200   254,829,864
|  |  |-  java.util.concurrent.ConcurrentHashMap @ 0xd9f15260        64   254,829,928
|  |  |  |-  class io.leaklab.leak.CustomerSessionCache  System Class  224   254,830,240
Technically

The reference chain from one instance back to a GC root. Weak, soft and finalizer references are excluded because they don't keep objects alive. Read it bottom-up: a System Class root (a loaded class, so one of its static fields) → a ConcurrentHashMap → bucket slot [44] → a node → the context. This is the proof. In code, CustomerSessionCache's static map is SESSIONS, written by remember(), which is called from CheckoutService.process(…, retryAware=true).

Like I'm five

Follow the string from one folder: to a tag, to a rack, to a basket, to the hook on the wall. Now you know exactly which hook to remove, and the cleaner will do the rest.

Architect's note

A finding is ready to act on when you can state it like this: "static CustomerSessionCache.SESSIONS retains 971 SessionContexts (254 MB, 81 % of the heap), growing one per retry-aware request, because entries are keyed by a unique requestId and never evicted." That names the root, the size, the growth law and the mechanism. It is precise enough to fix and to verify.

Native delta: anything growing outside the heap?

nativemem-diff.sh
sized:  VERDICT: no significant native growth (largest Δ 1.8 MiB)
Technically

Two javacores from the same JVM are parsed into NATIVEMEMINFO category paths and subtracted. For sized nothing grows outside the heap, so the investigation is complete: a pure heap leak.

E11

When the tool points the wrong way: the native scenario

BASELINE=- analyzer /dumps/semeru-25/native
Real output (guardian dump and javacores from Scenario D)
Heap context — heap in the dump ≈ 56 MiB of a 384 MiB maximum (15%).
GC trend      VERDICT: slight rise (+13.3 MiB, 3% of max heap) — not conclusive
MAT suspect   One instance of io.leaklab.load.LoadEngine_ClientProxy occupies 25,165,984 (42.80%) bytes ...
              The memory is accumulated in one instance of byte[]
NATIVEMEMINFO +625.6 MiB  +969 allocs  JRE > Class Libraries > VM Class Libraries > sun.misc.Unsafe > Other
VERDICT: native growth of 625.6 MiB in "… > sun.misc.Unsafe > Other"
Technically

MAT's Leak Suspects report always names something. Here it names the 24 MiB parachute at "42.80 %". But that is 42.8 % of a 56 MiB heap, which is 15 % of -Xmx, with a flat live set. The real leak is in step E10: 969 native allocations totalling 625.6 MiB, in the category where FFM Arena and Unsafe allocations land. That's why the summary reports heap context first: percentages in MAT are relative to the heap in the dump, not to the process or the container.

Like I'm five

The detective only looked at photos of the storage room, and pointed at the biggest thing there, the emergency sandbag. But the storage room was nearly empty. The living-room report showed 969 new crates. Always check how full the room is before blaming what's in it.

Pitfall

"Fixing" the top Leak Suspect without checking heap context, growth (E5) and native memory (E10) is the most common way heap analysis goes wrong. Leak Suspects is a hypothesis generator, not a verdict.

Part E · key takeaways
  • Analyse dumps in a separate, sized, controlled workbench. Never in the production pod.
  • Follow the order: trend → hypothesis → composition → growth → dominators → owners → instances → proof → off-heap. Each step answers one question.
  • Check the tools against ground truth when you can. Here, 971 objects and 254.5 MB matched the app's own counters.
  • Always read heap context before trusting a percentage. A "42 %" suspect can be a harmless sandbag.
  • Batch mode makes the analysis repeatable and attachable to incidents. The GUI is for exploring.
