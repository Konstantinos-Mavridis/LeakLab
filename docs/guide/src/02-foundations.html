1.1 Process memory: reserved, committed, resident

"How much memory does this process use?" has at least three correct answers. Confusing them is the most common source of wrong conclusions in this field.

Technically
  • Reserved: virtual address ranges a process has mapped (mmap with no access, or untouched). On 64-bit systems this is cheap and can be enormous. VmSize in /proc/<pid>/status.
  • Committed: memory the process has asked the OS to make usable. With Linux overcommit this is still mostly a promise. JVM MXBeans report "committed" per pool.
  • Resident (RSS): pages that are actually in physical RAM. A page becomes resident the first time it is touched (a page fault allocates it). VmRSS; the peak is VmHWM.

The memory cgroup charges a page to the container when it is faulted in. That is why LeakLab's leaking code writes one byte into every 4 KiB page it allocates: an untouched allocation would never show up in RSS or in the cgroup's usage.

Like I'm five

Reserved is putting your name on a list for a parking spot. Committed is the attendant saying "yes, you may park there". Resident is your car actually standing in the spot. The building only runs out of space when real cars are parked. Lists and promises take no room.

In the lab · a real example of the difference

On OpenJ9 the JIT code cache pool reported committed = 256 MiB while used = 2.6 MiB, and the whole process RSS was only 93 MiB. A first version of LeakLab added "committed" numbers and concluded the JVM needed 333 MiB outside the heap, which was clearly impossible. The fix was to measure RSS. Lesson: committed is not resident.

Architect's note

When you budget memory for containers, budget resident memory. Dashboards that show "virtual" or "committed" will mislead you. In Kubernetes, the metric that matters is container_memory_working_set_bytes, which is close to RSS plus active page cache (see 1.2).

1.2 Containers, cgroups and the OOM killer

A container is not a small virtual machine. It is an ordinary Linux process with two kernel features applied: namespaces (what it can see) and control groups (what it can use). Memory limits come from the second.

Technically
  • Namespaces isolate views: PID, network, mount, user, and so on. That is why the JVM is PID 1 inside the container.
  • cgroup v2 (the default on current Docker, Kubernetes and OpenShift 4.14+) exposes memory control as files in /sys/fs/cgroup: memory.max (hard limit), memory.current (charged bytes), memory.stat (breakdown), memory.peak (high-water mark) and memory.events (counters: max, oom, oom_kill).
  • Charged memory includes anonymous memory (heap, stacks, malloc), page cache for files the container reads and writes, and some kernel memory. Page cache is mostly reclaimable. tmpfs (/dev/shm, emptyDir.medium: Memory) is not.
  • Working set = memory.current − inactive_file. This is what the kubelet reports and acts on. LeakLab computes it the same way.
  • When a page fault would push usage over memory.max, the kernel first tries to reclaim: it evicts clean page cache and swaps if swap is allowed. Each such event increments memory.events: max. If reclaim cannot free enough, the memory-cgroup OOM killer picks a process in that cgroup (highest oom_score) and sends it SIGKILL (signal 9). The kernel log records oom-kill: constraint=CONSTRAINT_MEMCG … Killed process <pid> (java).
  • The container runtime sees the process exit with status 137 = 128 + 9 and records it as OOMKilled.
Like I'm five

The building has many apartments. The landlord measures each apartment's floor with a tape measure (the cgroup). When you bring in one more box than fits, the landlord first tidies your hallway (throws out old newspapers: page cache). If there's still no room, the landlord doesn't negotiate. They pick the biggest thing in your apartment, which is usually you, and put it on the street. The note on the door just says "137".

Why this mechanism exists

Limits protect neighbours. Without them, one leaking service could starve every other workload on the node. SIGKILL is used because it is the only signal a misbehaving process cannot ignore. That robustness is exactly why the process can do nothing to save evidence.

Cast
ComponentRepresentsRole

Pitfall

Exit code 137 alone does not prove a memory problem. It only means SIGKILL. A failed liveness probe, docker kill or a stop-timeout also produce 137. The proof is the runtime's reason field (OOMKilled) or the kernel log line.

1.3 The JVM, OpenJ9 and IBM Semeru

Technically

The Java Virtual Machine runs Java bytecode. It loads classes, interprets them at first, then JIT-compiles hot methods to native code. It manages memory automatically with a garbage collector. Two production JVM implementations matter:

  • HotSpot: the JVM in Oracle JDK, Temurin, Red Hat build of OpenJDK, and others.
  • Eclipse OpenJ9: originally IBM's J9. It is tuned for a small footprint and fast start-up, and has its own diagnostics (javacore, PHD, -Xdump) and its own GC policies (default gencon).

IBM Semeru Runtime Open Edition is IBM's free distribution: OpenJDK class libraries + OpenJ9 VM. LeakLab's default JVM is HotSpot, the Red Hat build of OpenJDK 21; the evidence in this guide comes from Semeru 25.0.4 (Java 25 LTS), and every JVM runs on Java 17, 21 and 25. The Java code is identical on both JVMs and all versions. Memory pool names, dump formats and tooling differ.

Like I'm five

Java programs are written in a language computers can't run directly. The JVM is a translator who reads the program aloud to the computer. It gets faster the more it reads the same sentences (that's the JIT), and it keeps the room tidy as it goes (that's the GC). HotSpot and OpenJ9 are two different translators. They speak the same language, but they keep their notebooks in different formats.

Architect's note

Diagnostics are part of the runtime choice. Choosing Semeru means your runbooks, tooling (MAT + DTFJ, GCMV) and team skills must cover PHD, javacore and -Xdump. Don't write a HotSpot-only runbook (jmap, NMT, HPROF) for an OpenJ9 fleet. Part 1.8 maps one to the other.

1.5 Garbage collection and the live set

Technically
  • Reachability decides what's kept. A GC starts from GC roots (static fields of loaded classes, local variables on thread stacks, JNI references, active monitors) and follows every reference. Whatever it can't reach is garbage, however large.
  • Generational hypothesis: most objects die young. gencon allocates new objects in the nursery using per-thread TLHs (thread-local heaps: lock-free bump-pointer allocation). When the nursery fills, a scavenge copies the few survivors and discards the rest. Objects that survive several scavenges are tenured.
  • Tenure is collected by global GC: a concurrent mark, a short stop-the-world final phase, a sweep, and compaction when fragmented. OpenJ9 expands the heap after a GC when free space is below -Xminf (30 % by default), up to -Xmx.
  • The live set (heap after a global GC) is the true size of what the application holds. Plotted over time, a healthy service draws a sawtooth with a flat floor.
Like I'm five

The cleaner comes often to the "new stuff" corner by the door. Most of it is wrapping paper, so it gets thrown away quickly (scavenge). Things that are still wanted after a few visits move to the back room (tenure). Sometimes the cleaner does the whole apartment (global GC). To check whether the household is hoarding, don't look at the mess on a busy afternoon. Look at how full the place is right after a full clean. If that number creeps up every week, something is hoarding.

Architect's note

Alert on the trend of the post-GC floor, not on "heap usage > 80 %". Heap usage is supposed to be high between collections. Alerting on it creates noise that teaches teams to ignore memory alerts.

1.6 What a "leak" means in Java

Technically

In a garbage-collected language a leak is unintended reachability: objects the program will never use again but still references from a GC root, so the collector must keep them. Typical forms are unbounded caches and maps (LeakLab's case), listeners that are registered but never removed, ThreadLocals on pooled threads, collections used as queues without consumers, and class-loader leaks on redeploy. The defining property is that retained size grows with cumulative work (total requests served), not with concurrent work.

Like I'm five

The cleaner is very obedient: anything tied to a hook stays. Someone tied a big basket to a hook and puts every receipt into it "just in case", but never looks at them again. The cleaner isn't broken; they were told to keep it. The basket grows a little with every customer until the room is full.

Why LeakLab's leak is realistic

CustomerSessionCache is meant to answer retried requests from memory, but it is keyed by requestId, which is unique per request. It can never produce a cache hit and never evicts. This "cache keyed by a unique ID" bug appears regularly in production code reviews.

1.7 OutOfMemoryError

Technically

java.lang.OutOfMemoryError is thrown by the JVM when an allocation can't be satisfied within a limit the JVM enforces. The message tells you which limit:

MessageMeaning
Java heap spaceAfter a full (global) collection and compaction, there is still no room for the object within -Xmx. OpenJ9 also throws this when the JVM spends nearly all of its time in GC (excessive GC detection).
Cannot reserve … bytes of direct buffer memory (older JDKs: Direct buffer memory)-XX:MaxDirectMemorySize would be exceeded. Thrown by Java code in java.nio.Bits, not by the VM, so the default OOM dump agents (and HotSpot's HeapDumpOnOutOfMemoryError) don't react to it (1.8)
Metaspace / class storageClass metadata exhausted (HotSpot MaxMetaspaceSize)
unable to create native threadThe OS refused a new thread (pid or thread limits, memory)

It is an Error, not an Exception: it propagates up the stack of the allocating thread, which is not necessarily the thread that leaked. Before it is thrown, OpenJ9's dump agents run (1.8).

Like I'm five

The tenant tries to put one more box in the storage room. First they ask the cleaner to do a full, careful clean. If there's still no room, they stop and say out loud, "the storage room is full." Because they are still in charge of their apartment, they can take photos and write notes before deciding what to do.

Pitfall

A JVM that has thrown OOM is in an undefined state. Any thread may have failed half-way through an operation. LeakLab demonstrates a nasty variant in A9. Production services should normally exit after the dumps are written (-XX:+ExitOnOutOfMemoryError) and let the platform restart them.

Technically · dump agents

OpenJ9 attaches dump agents to events, configured with -Xdump. Out of the box, on the first systhrow java/lang/OutOfMemoryError the JVM writes a system dump (once), and a heap dump, javacore and snap trace (up to 4 times each). user is the event for SIGQUIT (kill -QUIT), which by default produces a javacore. systhrow means "thrown by the VM itself". An OOM thrown by Java code, such as the direct-buffer error, is a plain throw event, and no default agent listens for it (verified: no dumps at all). LeakLab's image adds:

-Xdump:directory=/dumps        # every artefact goes to the mounted volume
-Xdump:heap:events=user        # kill -QUIT 1 also produces a heap dump (no jcmd needed)
# an OOM thrown by Java code (direct buffers), which no default agent catches:
-Xdump:java+heap:events=throw,filter=java/lang/OutOfMemoryError,msg_filter=*direct*,range=1..1
# 5 rotating files, 20k GC cycles each; start time in the name survives restarts:
-Xverbosegclog:/dumps/verbosegc.%Y%m%d.%H%M%S.%pid.%seq.log,5,20000

Dumps can also be triggered by API (com.ibm.jvm.Dump.heapDumpToFile, which LeakLab's buttons use), by jcmd in JDK images, or by special events such as large allocations (events=allocation,filter=#256m).

Like I'm five

The tenant keeps a camera and notebook by the door, set to go off automatically on certain alarms: "storage room full" or "someone rang the special bell (SIGQUIT)". The photo album is the heap dump, the written report is the javacore, and the cleaner keeps a diary all the time (the GC log). None of it helps if the landlord evicts you without warning. That's why the diary lives in a safe outside the apartment (the volume).

Architect's note

Treat dump configuration as platform standard, not an incident-time activity: dump directory on a persistent volume, agents enabled, GC log rotating, a tested copy-out procedure. Dumps also contain whatever the application held in memory: session data, tokens, personal data. Classify them as production data, with access control, encryption and retention.
