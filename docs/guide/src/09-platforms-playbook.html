Docker is one apartment that you manage yourself. Kubernetes is a large building with a management office that rehouses evicted tenants automatically. OpenShift is that building with a security desk, an in-house carpentry workshop (BuildConfig) and a reception with a guest list (Routes).

6.2 Deploying to OpenShift, step by step

P1

oc new-project leaklab

Technically: creates a namespace with OpenShift's default RBAC, quotas and SCC bindings. ELI5: renting a floor in the building for this experiment. Why: isolation and easy clean-up (oc delete project leaklab).

P2

oc apply -k deploy/openshift

Technically: Kustomize renders the base Deployment, Service and PVC three times (overlays sized, overcommit, native) with name suffixes, scenario labels in selectors, and per-scenario env and limits. It adds the ImageStream, BuildConfig and three Routes, and patches each Deployment with an ImageStream trigger and image-lookup annotation. ELI5: one set of blueprints, photocopied three times with different room sizes written in. Why: one source of truth. The only differences between scenarios are the ones you intend.

P3

oc start-build leaklab --from-dir=app --follow

Technically: uploads your working copy as a binary build input. buildah runs the multi-stage Containerfile in a build pod, on the default UBI 9 runtime (the Red Hat build of OpenJDK 21), and pushes to the internal registry as leaklab:latest. The ImageStream tag update triggers rollouts of all four Deployments. ELI5: the building's own workshop builds the furniture from your drawings and delivers it to the four apartments. Why: no external registry or CI needed. Note the 2 GiB limit on the build pod itself, since Maven also needs memory.

P4

Pods start under restricted-v2

Technically: the pod gets a random UID in the project's range with supplementary group 0. The group-writable /dumps and /deployments make that work. The PVC is bound and mounted. The startup probe gates the readiness and liveness probes. terminationMessagePolicy: FallbackToLogsOnError is active. ELI5: the security desk gives each tenant a random badge number. The apartment has to let any badge from the right "family" in.

P5

Run the scenarios through the Routes

Technically: the Routes terminate TLS at the edge, with a 10-minute HAProxy timeout for the SSE stream and large downloads. After a kill, inspect with oc get pod … lastState, oc logs --previous and scripts/oomkill-forensics.sh k8s leaklab, and copy dumps with scripts/collect-evidence.sh k8s leaklab deploy/leaklab-native.

Pitfall · QoS precision

The manifests set memory requests == limits but only a CPU request, so the pod's QoS class is Burstable, not Guaranteed (Guaranteed needs requests = limits for both CPU and memory). Equal memory request and limit still means the container never uses more memory than it reserved, which keeps it low in the node-pressure eviction order. The kill you will see is the cgroup OOMKill at its own limit.

Part 7

The architect's playbook

Everything above, condensed into design rules, a sizing method, an observability baseline and an incident decision tree. This is the part to take into your next design review.

7.1 Ten design rules

  1. The JVM fails first. heap ceiling + non-heap footprint + headroom < container limit, always.
  2. Size by percentage, not by number. -XX:MaxRAMPercentage, never a hard-coded -Xmx that can drift away from the limit.
  3. Cap every capturable native consumer: MaxDirectMemorySize, thread pools, -Xss, MALLOC_ARENA_MAX.
  4. Memory request = memory limit for JVM workloads: predictable placement, and no overcommit surprises.
  5. Evidence by default: dump directory on a PVC, OpenJ9 agents on, rotating GC log, a tested copy-out procedure.
  6. Evidence before the limit: guardian or alert-driven automation at ~85–90 % working set.
  7. Fail fast after OOM: -XX:+ExitOnOutOfMemoryError once the dumps are written.
  8. Liveness never measures memory, and tolerates GC and dump pauses.
  9. Every cache states its bound and eviction policy in code review. Unbounded maps fail review.
  10. Dumps are sensitive data: classification, access control, encryption, retention.

7.2 Sizing method

Technically
  1. Run a soak test at peak load. Record the steady-state live set (after global GC) and the non-heap footprint (RSS − heap committed).
  2. Heap ceiling ≈ live set × 2–3, so the GC has room to work efficiently.
  3. Limit ≈ heap ceiling + non-heap footprint × 1.3 + 10 % margin.
  4. Express the heap as MaxRAMPercentage = heap ÷ limit.
  5. Validate: the LeakLab-style verdict is SIZED; a forced heap leak in staging ends in a Java OOM with dumps, not an OOMKill.
Like I'm five

Measure how much stuff the household really keeps, then give the storage room two or three times that so the cleaner has space to work. Add the furniture, plus a bit extra, and that's the apartment size. Then test it: overfill the storage room on purpose and check that the tenant raises the alarm before the landlord evicts them.
