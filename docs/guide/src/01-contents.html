The big picture on one page

A Java service in a container lives inside two memory budgets, enforced by two different parties. Nearly everything in this guide follows from that one fact.

Technically

The JVM enforces -Xmx (heap) and -XX:MaxDirectMemorySize (direct buffers). Crossing either produces a java.lang.OutOfMemoryError. That is a controlled failure: diagnostic dump agents run and the process can keep going or exit cleanly.

The kernel enforces the cgroup's memory.max on everything the process has resident: heap, non-heap, direct, native and some kernel memory. When a page fault would cross the limit and reclaim fails, the memory-cgroup OOM killer sends SIGKILL. That is an uncontrolled failure. The process cannot react to it.

Like I'm five

The JVM is a tidy tenant who keeps a strict rule for their own storage room: "never more than this many boxes." If the storage room fills up, they stop, write a neat note explaining what's in it, and ask for help.

The kernel is the landlord, and the apartment has a fixed size. If the tenant's stuff, storage room and furniture together, no longer fits, the landlord doesn't knock. They change the locks and throw everything out, notes included.

Architect's note

The design goal is simple to say: make the JVM hit its own limit before the kernel hits the container's. Then failures are diagnosable. In practice that means heap ceiling + non-heap footprint + headroom < container limit, with every native consumer capped or measured. Part 7 turns this into a checklist.

The four scenarios at a glance

LeakLab runs one container image four times, with different memory settings. The leaking code is identical. Only the configuration changes, and with it the way the service dies and what evidence survives. The scenarios are ordered by how hidden the cause is: from a JVM that catches its own leak, to a kill that no JVM flag could prevent.

Why four scenarios

Together they cover the four answers to "why did my Java container die of memory?": (A) the application leaked and the JVM caught it; (B) the configuration put the heap ceiling above the container limit, visible in one flag; (C) the heap fits, but the JVM's other memory has no room, because a percentage sizes only the heap and direct buffers default to a cap the size of the heap; (D) the leak is in memory that no JVM flag can bound. Each needs different evidence and a different fix, so recognising which one you are in is the first diagnostic skill.

And one for your own numbers: M · manual (port 8084)

A fifth service runs the same image with the limit, CPUs and JAVA_OPTS you give it, by default 1 GiB and MaxRAMPercentage=75, on the JVM and Java version of the env file you pass. It is what a plain docker compose up starts; --profile all starts A–D and G. The verdict banner says before any load which of the four you have built. Commands in Appendix B.
