Part 2

The lab: components, flows and start-up

Before running any scenario, meet the cast: every class and every piece of infrastructure, what it stands for in a real system, and how data and evidence move between them. Then follow a container from docker compose up to a live dashboard.

2.2 Request, telemetry and evidence flows

① Request flow

  1. A LoadEngine tick picks the batch size.
  2. For each request it draws a random number: below the retention % means the leaking path.
  3. Heap mode: CheckoutService.process allocates the byte[] and touches each page.
  4. Leaking path: CustomerSessionCache.remember(ctx), so the context is now reachable from a static field.
  5. Otherwise the context becomes garbage when the method returns ("churn").
  6. Direct/Native modes do the same with a vault instead of the cache.

② Telemetry flow

  1. The browser opens an EventSource to /api/telemetry/stream.
  2. Every second Mutiny emits a tick on a worker thread.
  3. MemoryProbe.read() collects heap, pools, collectors, buffer pools, RSS and cgroup values, then computes the verdict.
  4. Load stats, guardian state, recent GC events and the journal are added.
  5. Jackson serialises it to JSON; the SSE frame reaches the browser.
  6. app.js appends it to a 5-minute history and redraws.

③ Evidence flow

  1. A trigger fires: a UI button or REST call, kill -QUIT 1, an OOM event, or the guardian.
  2. The JVM requests exclusive access (all Java threads pause).
  3. The agent walks the heap or collects the report and writes it to /dumps.
  4. Threads resume. The file survives on the volume, even after a kill.
  5. Copy out: UI download, docker cp, kubectl cp.
  6. Analyse: MAT + DTFJ (PHD), a text editor (javacore), GCMV (GC log).
Like I'm five

① Customers keep arriving and each one leaves a parcel. Most parcels are thrown away after use, but a set percentage are wrongly stuffed into the hoarding basket. ② A helper looks at every room once a second and calls out the numbers to a big scoreboard. ③ When an alarm goes off, everyone freezes for a moment while photos are taken, and the photos go straight into the basement locker.

2.3 From docker compose up to a live dashboard

These steps happen in every scenario. Only the numbers in S3 and S5 differ.

S1

Build stage: compile the application

Containerfile · stage "build"
Technically

A multi-stage build starts from maven:3.9.16-ibm-semeru-25-noble, which has a full JDK and Maven. mvn dependency:go-offline caches dependencies in their own image layer. mvn package then compiles bytecode for the selected Java release, 25 or 21 (javac --release, so one JDK 25 builder serves both), and runs Quarkus's build-time augmentation, which resolves dependency injection, REST routes and configuration ahead of time. The output is the "fast-jar" layout in target/quarkus-app.

Like I'm five

In a workshop with every tool available, the furniture is built and flat-packed. The workshop isn't shipped, only the flat-packed furniture.

Why

The runtime image never contains compilers or Maven: it is smaller and has a reduced attack surface. Doing work at build time is why Quarkus starts in about 1.7 s.

S2

Runtime image: a JRE plus the app

stage 2
Technically

The runtime stage used in this guide is ibm-semeru-runtimes:open-25-jre-noble (OpenJ9), or UBI 9 minimal for OpenShift through a build argument. It copies the fast-jar, makes /deployments and /dumps owned by group 0 with group-write permission, and switches to USER 1001. It sets two environment variables: JAVA_OPTS (sizing, overridden per scenario) and JAVA_DIAG_OPTS (dump directory, heap dump on SIGQUIT, dumps for a direct-buffer OOM, rotating verbose GC log). Build arguments pick the VM family, the distribution and the Java release, 17, 21 or 25. The default is a HotSpot JDK, the Red Hat build of OpenJDK 21 on UBI 9, with HotSpot's own diagnostics. Twelve env files, <jvm>-<version>.env (redhat-21.env, semeru-25.env, …), set all three (Appendix C).

Like I'm five

A clean, empty apartment with just the furniture you need, a camera already mounted by the door, and a diary on the table.

Architect's note

Group-0 permissions exist because OpenShift runs containers as a random UID that belongs to group 0. An image that only works as root or as one fixed UID will fail under the default restricted-v2 security context constraint.

S3

Container creation: the cgroup is born

compose.yaml
Technically

Docker asks containerd/runc to create the namespaces and a cgroup. mem_limit: 1g becomes memory.max = 1073741824. memswap_limit equal to mem_limit means zero swap, so the container is killed rather than thrashing. ./dumps/<jvm>-<version>/<scenario> is bind-mounted at /dumps. restart: "no" keeps a dead container's state for inspection. On Docker Desktop all of this happens inside its Linux VM. That VM is the "node".

Like I'm five

The landlord draws chalk lines on the floor: "this is your space, and no borrowing from the corridor (swap)." The diary's safe is bolted in the basement (bind mount).

S4

Entrypoint: exec java becomes PID 1

Technically

/bin/sh -c "exec java $JAVA_DIAG_OPTS $JAVA_OPTS … -jar quarkus-run.jar": the shell expands the environment variables, then exec replaces itself with the JVM. Java becomes PID 1, so SIGTERM from docker stop and SIGQUIT from kill -QUIT 1 reach the JVM directly.

Like I'm five

The receptionist who opened the door steps aside completely, so when someone rings the bell, the tenant answers, not the receptionist.

Pitfall

Without exec, a shell stays as PID 1, signals don't reach Java, graceful shutdown breaks, and kill -QUIT 1 produces nothing.

S5

JVM bootstrap: reading the container and sizing the heap

Technically

OpenJ9 detects that it is running in a container (cgroup v2) and reads memory.max. With -XX:MaxRAMPercentage=60 on 1 GiB it sets the maximum heap to 614 MiB and reserves that address range (reserved, not resident; see 1.1). An explicit -Xmx overrides this, even if it is larger than the limit (Scenario B). The JVM then initialises gencon, registers the default and configured dump agents, opens /dumps/verbosegc.1.001.log, loads core classes from the shared class cache and starts JIT compiler threads.

Like I'm five

The tenant measures the apartment and decides: "my storage room will be at most 60 % of the floor." But if someone hands them a note saying "use 1 GiB of storage", they obey the note, even if the apartment is only 512 MiB.

In the lab

The JVM records what it saw in every javacore's ENVINFO section (real excerpt, native scenario):

1CICONTINFO    Running in container : TRUE
1CICGRPINFO    JVM support for cgroups enabled : TRUE
3CICGRPINFO        Memory Limit : 805306368 bytes      # 768 MiB
3CICGRPINFO        Swap Limit : 0 bytes
S6

Quarkus boot

Technically

Quarkus loads its pre-computed wiring, instantiates the CDI beans it needs, starts the Vert.x HTTP server on port 8080 and fires StartupEvent. Real log: leaklab 1.0.0 on JVM (powered by Quarkus 3.40.1) started in 1.757s.

S7

LeakLab's start-up hooks

Technically
  • GcWatcher registers a listener on every GarbageCollectorMXBean (OpenJ9: scavenge and global) to receive before/after usage per pool.
  • LoadEngine starts its daemon thread, idle until engaged, and allocates a 24 MiB parachute (explained in A9).
  • DumpService checks that /dumps is writable and loads com.ibm.jvm.Dump reflectively, which tells it this is OpenJ9.
  • TelemetryResource builds and serialises one snapshot (a warm-up).
  • OomGuardian is scheduled every second. LeakMetrics registers its gauges.
Why the warm-up

Some JVM call sites are linked lazily on first use, and linking needs memory. Doing it at boot means the telemetry path still works when the heap is full later.

S8

The browser connects and the verdict appears

Technically

index.html, CSS and JS are served from META-INF/resources, with no CDN, so it works air-gapped. The page fetches /api/load and opens the SSE stream. From the first snapshot, the verdict compares heap ceiling + native footprint + direct allowance (native footprint = RSS − heap committed; direct allowance = how far direct buffers may still grow before their cap) with the cgroup limit and classifies the setup as SIZED, TIGHT, OOMKILL_LIKELY or OOMKILL_BY_DESIGN.
