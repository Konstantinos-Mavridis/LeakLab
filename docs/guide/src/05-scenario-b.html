Scenario B · port 8081

overcommit: the silent kill

The same leak as Scenario A, with one configuration mistake that is common in real estates: a heap ceiling larger than the container. The JVM never runs out of memory. The kernel kills it first, and every diagnostic the JVM could have produced is lost.

B1

Configuration and verdict

compose: overcommit
mem_limit: 512m    memswap_limit: 512m
JAVA_OPTS: "-Xmx1g"
LEAKLAB_GUARDIAN_ENABLED: "false"     # on purpose: watch it die with zero evidence
Technically

An explicit -Xmx overrides container-aware sizing. The JVM knows the cgroup limit (it is in the javacore), but -Xmx is an instruction, so it is obeyed. Heap ceiling 1024 MiB plus non-heap ~78 MiB gives 1102 MiB projected, against a 512 MiB limit: OOMKILL_BY_DESIGN. The heap is allowed to grow into memory the kernel will never grant.

Like I'm five

Someone gave the tenant a note: "your storage room may hold 1,000 boxes". The apartment only fits 512 boxes' worth of everything. The tenant trusts the note. Nobody is lying, but the two rules disagree, and only one of them is the landlord's.

Why this happens in real life
  • -Xmx copied from a VM or bare-metal deployment into a container template.
  • The container limit was lowered later (cost optimisation), but JAVA_OPTS wasn't touched.
  • Helm or Kustomize values for limits and JVM flags are owned by different teams.
  • "Java needs 1 GiB" folklore, applied without measuring.
B2

The heap grows freely

t = 0 → ~15 s
Technically

The leak runs at 20 MiB/s, as in A7. Each global GC finds the live set larger. Free space after GC drops below -Xminf, so OpenJ9 expands the heap. From the JVM's point of view this is healthy: it is still far below its 1 GiB ceiling, so there is no reason to collect harder, compact more or throw. Neither OpenJ9's nor HotSpot's default GC heuristics react to the cgroup getting full. They react to heap occupancy relative to the heap's own limits.

Each expansion commits more heap, and as objects are written into it, more pages become resident and are charged to the cgroup.

Like I'm five

The storage room keeps getting bigger, because the note says it may. The tenant doesn't feel crowded at all: by their own rule, half the allowed storage is still free. They have no idea the apartment walls are getting close.

In the lab · the UI at the last snapshot before death

Java heap 423 MiB, 41 % of -Xmx (tag: OPENJ9, green). Container working set 507 MiB, 99 % of the 512 MiB limit (tag: KILL ZONE). Two panels side by side, telling opposite stories. That contrast is the whole lesson of this scenario.

B3

The container approaches its limit

t ≈ 15 → 21 s
Technically
  1. Each new page fault charges 4 KiB to the cgroup. memory.current approaches memory.max.
  2. To make room, the kernel runs direct reclaim inside the cgroup. It drops clean page cache and file-backed pages (mapped JARs, the shared class cache), which can be re-read from disk later. Each time the limit is hit, memory.events: max increments. This is visible in LeakLab's Kernel's view.
  3. There is no swap (memswap_limit = mem_limit), so anonymous memory such as the Java heap cannot be moved out of RAM.
  4. Performance may wobble (file pages fault back in), but nothing in the JVM or application logs warns of what is coming.
Like I'm five

The landlord notices the apartment is over the line and starts quietly removing things that can be fetched again later: the newspapers, the library books. But the boxes in the storage room can't be put anywhere else. There is no corridor (swap). Soon there is nothing left to remove.

Architect's note

memory.events max and a working set above ~90 % of the limit are your last early warning. After that comes SIGKILL. Alert on these, and automate evidence capture at this point. That is the guardian pattern in D4.

B4

The kernel's OOM killer acts

t ≈ 21 s · 09:57:39
Technically

A page fault cannot be charged and reclaim made no progress, so the memory-cgroup OOM path runs. The OOM killer scores the processes in this cgroup (essentially by memory size plus oom_score_adj), picks java, and sends SIGKILL. SIGKILL cannot be caught, blocked or handled: the kernel tears the process down directly. The kernel log records oom-kill: constraint=CONSTRAINT_MEMCG … Killed process 1 (java) … anon-rss:…. memory.events increments oom and oom_kill. The runtime receives the OOM notification and the exit status 137.

Like I'm five

The landlord walks in mid-sentence, picks up the tenant and puts them on the street. There is no time to grab the camera, finish the diary page or say goodbye. The door closes.

Like I'm five

When you come back, the apartment is empty. No photos, no notes, no goodbye letter. The only clue is the cleaner's diary, which was kept in the basement locker. Its last page says "storage room half used, plenty of space left". The tenant had no idea.

Purpose

To learn that absence of evidence is evidence. A memory death with no JVM dump lines and an abruptly ending log is, almost by definition, a kill from outside.

B6

The same death on Kubernetes / OpenShift

Technically
  1. The kubelet sees the container exit with reason OOMKilled, exit code 137, and records it in status.containerStatuses[].lastState.terminated.
  2. Because the Deployment's restartPolicy is Always, the kubelet restarts the container in the same pod and increments restartCount. Repeated failures back off exponentially, which shows as CrashLoopBackOff.
  3. terminationMessagePolicy: FallbackToLogsOnError copies the last log lines into lastState.terminated.message.
  4. The pod-level view keeps the evidence of the previous instance. oc logs --previous shows its log.
  5. Metrics: kube_pod_container_status_last_terminated_reason{reason="OOMKilled"}, kube_pod_container_status_restarts_total, and container_oom_events_total.
$ oc get pod -l leaklab.io/scenario=overcommit -o jsonpath='{..lastState.terminated.reason} {..lastState.terminated.exitCode}'
OOMKilled 137
$ oc describe pod leaklab-overcommit-…      #  Last State: Terminated · Reason: OOMKilled · Exit Code: 137 · Restart Count: 3
Like I'm five

The building office immediately moves an identical new tenant in, who then gets evicted in exactly the same way. From the street the apartment looks occupied most of the time. You only find out by reading the office's eviction log (lastState, restartCount).

Pitfall

Auto-restart hides OOMKills. Services look healthy between deaths, and error rates show only short blips. Always alert on restarts with reason="OOMKilled".

Scenario B · key takeaways
  • Two limits, two enforcers. The JVM's safety net only works if its limits sit inside the kernel's.
  • The JVM's GC does not react to container pressure. With -Xmx above the limit, it will happily expand into a kill.
  • An OOMKill leaves no JVM evidence. Plan for evidence before the limit (guardian, alerts) and keep the GC log on a volume.
  • Exit 137 means SIGKILL. The reason field means memory. Check both.
  • Auto-restart hides the problem. Alert on restart reasons.

B · Forensics readiness: what must be in place to prove an OOMKill

After a SIGKILL the JVM can do nothing, and its dump agents never run. Proving what happened and why depends on evidence kept outside the dead process: a GC log on a volume, the runtime's termination record, platform metrics and the node's kernel log. Each of these has to exist before the kill. Nothing can be enabled afterwards.
