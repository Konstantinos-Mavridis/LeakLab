Scenario C · port 8082

greedy: the percentage trap

"We use MaxRAMPercentage, so we're container-aware and safe." This scenario tests that belief. Unlike B, nothing is obviously wrong: there is no -Xmx, and the heap ceiling fits inside the limit. It is an implicit overcommit. A percentage sizes the heap and nothing else, and the JVM's other memory, above all direct buffers with their default cap the size of the heap, has nowhere to go.

C1

Configuration and verdict

In the lab · real verdict, before any load (Semeru)
OOMKILL_LIKELY — Heap ceiling + native footprint exceed the limit
Heap ceiling 972 MiB + non-heap footprint 71 MiB + direct-memory allowance 972 MiB
(no MaxDirectMemorySize: default ≈ max heap) = 1.97 GiB, above the 1.00 GiB limit.

On HotSpot 25 (Oracle, Temurin) the heap and its non-heap just fit, so the verdict names the real culprit instead: "The off-heap allowance doesn't fit in the room left". HotSpot 17 and 21 need 20–40 MiB more outside the heap and read like Semeru, or fit by a few MiB. Red on all twelve variants.

Technically

95 % of 1 GiB gives a 973 MiB heap ceiling and leaves about 51 MiB for everything else. The JVM's own non-heap memory (class storage, JIT, threads, GC metadata, libraries) already needs 71–76 MiB at idle. And because MaxDirectMemorySize isn't set, direct buffers may grow to about the max heap, on top of the heap. The verdict adds all three ceilings: the JVM is allowed almost twice what the container has. The configuration is wrong before a single byte leaks.

Like I'm five

This time nobody handed the tenant a wrong note. The tenant measured the apartment themselves and decided "my storage room may use 95 % of the floor". But the bed and the desk need more than the remaining 5 %, and the crate rule allows as many crates as the storage room is big.

C2

The JVM did read the limit

javacore ENVINFO
3CICGRPINFO        Memory Limit : 1073741824 bytes        # 1 GiB: container detection worked
3CICGRPINFO        Memory Usage : 976297984 bytes         # 91 % when the guardian took this javacore
Technically

Container support worked as designed. OpenJ9 read memory.max and computed the heap ceiling from it. MaxRAMPercentage answers one question only: "how big may the heap get?". It doesn't reserve room for non-heap or direct memory. Being container-aware is necessary but not sufficient.

Like I'm five

The tenant did measure the apartment correctly. They just only planned for the storage room.

Technically

The heap sits flat at about 58 MiB the whole time. What grows is direct memory, which the heap dump barely shows: each buffer is a small DirectByteBuffer wrapper on the heap, and its native block is not in a PHD or HPROF. The guardian's javacore (OpenJ9) or VM report (HotSpot NMT) names the consumer exactly. The retained tile in the UI shows less than the javacore, because churned buffers are only freed by their Cleaner after a GC, and a flat heap rarely collects.

C4

Why no OutOfMemoryError was ever thrown

the direct cap's default
Technically

Without -XX:MaxDirectMemorySize, the direct cap defaults to about the max heap, here ≈ 973 MiB, in addition to the heap. A direct-buffer OutOfMemoryError ("Cannot reserve … bytes of direct buffer memory") would need direct memory to reach 973 MiB, and heap plus direct to approach 1.9 GiB, in a 1 GiB container. The kernel acts at 750–880 MiB of direct memory. The JVM's safety net was set higher than the trapdoor beneath it, on every JVM.

Like I'm five

By the tenant's own crate rule there was still plenty of room for crates, so the tenant never raised the alarm. The landlord was counting the whole apartment.

The fix, already in the lab

Scenario A's direct-buffer variant (A10) is this scenario with the cap set: MaxDirectMemorySize=96m turns the same leak into a Java OutOfMemoryError with dumps, and the process stays alive.

Technically

Heap committed grows in steps (83 → 137 → … → 500 → 646 → 841 → 973 MiB) as OpenJ9 expands the heap after GCs, until it reaches the ceiling. The working set tracks heap + non-heap. The guardian fires at 91 %, and the kernel kills the process at the limit about 86 s after the leak starts.

On HotSpot

With the same flags, the HotSpot 25 builds (Red Hat, Oracle, Temurin) end differently: HotSpot picks Serial GC and needs less non-heap memory, so it fits by about 9 MiB and throws a Java OutOfMemoryError instead of being killed. The margin is far too thin to rely on (Appendix C): in one run the container survived the leak at 1016 of 1024 MiB, and the sh started by docker exec to read memory.events was the allocation that triggered the kill. On Java 17 and 21 the same HotSpot needs 20–40 MiB more outside the heap, and all of them were killed again, including LeakLab's default, Red Hat 21: the margin moves with the Java version.

C6

A detail that matters: RSS above the limit?

Technically

At t = 85 s, RSS read 1,056 MiB, above the 1,024 MiB limit, while the cgroup working set read 1,016 MiB. RSS also counts file-backed pages shared with other processes (JDK libraries, mapped JARs) that may be charged to another cgroup or reclaimed. The kernel acts on the cgroup's own accounting. Alert on container_memory_working_set_bytes, and use RSS as a secondary signal.

C8

Fixing and checking

Technically
  • Choose the percentage from a measured non-heap footprint: limit − footprint − headroom. The playbook range is 50–60 % at ≤ 1 GiB.
  • Always cap direct memory (-XX:MaxDirectMemorySize). This turns C3 into a diagnosable OutOfMemoryError, as in Scenario A10.
  • One JVM per container. Audit JAVA_TOOL_OPTIONS.
  • Check what the JVM decided: OpenJ9 java -verbose:sizes -version and javacore 3CICGRPINFO Memory Limit; HotSpot -XshowSettings:system, -XX:+PrintFlagsFinal.
  • Keep the guardian or an equivalent alert at about 90 % of the working set. It captured evidence before the kill in nearly every run of this scenario, on all twelve variants. The exceptions: on HotSpot 17 and 21 the heap variant can jump from 83 % to 97 % between two polls, and in one run each on Oracle 21 and Red Hat 17 nothing was written in time.
Like I'm five

Measure the furniture first, then decide how big the storage room may be. Put a separate rule on the crates. And keep the smoke alarm.

Scenario C · key takeaways
  • MaxRAMPercentage makes the heap container-aware. It doesn't make the process fit.
  • B is an explicit overcommit you can see in one flag. C is implicit: every number looks reasonable on its own, and only their sum (heap ceiling + non-heap + direct allowance) exceeds the limit.
  • Uncapped direct memory effectively doubles the heap budget. Always cap it: then C becomes A10, a Java OOM with dumps.
  • The heap-leak variant is a knife edge: OpenJ9 was killed, HotSpot 25 survived by ~9 MiB, HotSpot 17 and 21 were killed again. Don't size that close: a JVM upgrade moves the margin.
  • Alert on the cgroup working set, not RSS. The guardian captured evidence before almost every kill; a fast jump between two polls can still beat it.

In the lab · options you didn't write (real javacore, greedy)
2CIENVVAR      JAVA_OPTS=-XX:MaxRAMPercentage=95
2CIENVVAR      JAVA_TOOL_OPTIONS=-XX:+IgnoreUnrecognizedVMOptions -XX:+PortableSharedCache -XX:+IdleTuningGcOnIdle
               -Xshareclasses:name=openj9_system_scc,cacheDir=/opt/java/.scc,readonly,nonFatal

The IBM Semeru base image sets JAVA_TOOL_OPTIONS itself. Here that's harmless (shared class cache, idle tuning), but it is a second source of options your deployment YAML doesn't show. Tested in this image, a misspelled sizing flag is a silent trap:

java -XX:MaxRamPercentage=60 -version                         # starts normally: typo silently ignored → default sizing
java -Xmxx1g -version                                         # JVMJ9VM007E Command-line option unrecognised → aborts
java -XX:-IgnoreUnrecognizedVMOptions -XX:-IgnoreUnrecognizedXXColonOptions -XX:MaxRamPercentage=60 -version
                                                              # JVMJ9VM007E … unrecognised: -XX:MaxRamPercentage=60 → aborts

OpenJ9 ignores unknown -XX: options by default, and the image's -XX:+IgnoreUnrecognizedVMOptions reinforces that. Setting -XX:-IgnoreUnrecognizedXXColonOptions alone is not enough while that variable is present. Both must be disabled for a typo to fail fast. In every case, read the effective options and the resulting heap size from the javacore rather than trusting the YAML.

Like I'm five

To prove the tenant planned badly, you need their written plan (the effective options), a measurement of the furniture (non-heap), and a separate count of the crates (direct memory). The plan and the crate count can be read any time. The crate limit and the smoke alarm have to be installed before moving in.
