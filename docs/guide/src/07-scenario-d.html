native: the leak the heap can't see

Everything the JVM can cap is capped, heap and direct memory, and a leak in native memory that no JVM limit governs. The heap dump comes back clean, and the evidence is somewhere else. This scenario also shows the guardian pattern capturing evidence seconds before an OOMKill.

D2

Native allocation through FFM

target "Native" · NativeMemoryVault
Technically
  1. The Foreign Function & Memory API (FFM, java.lang.foreign, final since Java 22) lets Java code allocate and access memory outside the heap. It is the modern, safe replacement for sun.misc.Unsafe and much JNI. On Java 17 and 21 FFM is not final yet (an incubator and a preview API), so those builds allocate with Unsafe.allocateMemory and setMemory instead. Below the API it's the same path, and the evidence is identical.
  2. Arena.ofShared().allocate(bytes, 64) obtains native memory from the C allocator through the JDK's internal unsafe allocation path, and returns a MemorySegment. The memory lives until the arena is closed.
  3. segment.fill((byte) 0x5A) writes every byte, so every page becomes resident and is charged to the cgroup.
  4. On the leaking path the arena is stored in a static deque and never closed. On the churn path a confined arena is closed immediately (try-with-resources), so its memory is freed.
  5. On the heap, each leak costs only small Arena/MemorySegment objects (a few hundred bytes), while each costs 512 KiB of native memory. The heap barely notices.
Like I'm five

Instead of boxes in the storage room, the tenant now orders big crates that are delivered straight into the living room. In the storage room they only keep a small receipt for each crate. The receipts weigh nothing, but the crates fill the apartment.

What this represents

Real native leaks come from JNI libraries (image processing, compression, crypto, database drivers), off-heap caches, Netty's pooled allocators misconfigured or not released, unclosed native resources, and glibc malloc arena growth under many threads. FFM gives the lab a clean, reproducible stand-in for all of them.

Architect's note

This is why platform dashboards must show container working set next to JVM heap. The gap between them, working_set − heap_used, is the native footprint, and its trend is the off-heap leak detector.

D4

The guardian fires

09:57:47 · 88 % of the limit
Technically
  1. OomGuardian runs every second on the Quarkus scheduler. It reads the cgroup and computes pressure = working set / memory.max.
  2. When pressure is ≥ 0.88 and the guardian is armed, it disarms, logs a CRITICAL journal entry, then writes a javacore first (cheap, and it contains NATIVEMEMINFO, the evidence that matters for a native leak) and a PHD second.
  3. It re-arms only when pressure drops below 0.75, so it doesn't fire on every tick.

Like I'm five

A smoke alarm is set to go off when the apartment is 88 % full. When it does, it quickly writes the household report (one tenth of a second), then takes the photo album (a quarter of a second), and puts both in the basement locker. Four seconds later the landlord arrives.

Why it worked, and when it wouldn't

Headroom at the threshold: 12 % of 768 MiB ≈ 92 MiB. At 20 MiB/s that is about 4.6 s of runway, and the evidence took ~0.35 s plus up to 1 s of polling delay. A faster leak, a larger heap (slower dumps) or a dump written to a memory-backed volume could miss the window. Tune the threshold to growth rate × (poll interval + dump time), with margin.

Technically · step 3, if NATIVEMEMINFO shows nothing growing

The memory isn't allocated by the JVM at all: a JNI library calling malloc directly, or glibc arena fragmentation. Use OS tools: pmap -x 1 | sort -k3 -n | tail, /proc/1/smaps_rollup, jemalloc profiling (LD_PRELOAD + MALLOC_CONF=prof:true). Try MALLOC_ARENA_MAX=2. On HotSpot the equivalent of NATIVEMEMINFO is Native Memory Tracking (-XX:NativeMemoryTracking=summary, jcmd 1 VM.native_memory summary.diff).

Scenario D · key takeaways
  • Correct heap sizing does not protect against native leaks. Only container-level monitoring sees them.
  • A clean heap dump plus a rising RSS is a diagnosis: off-heap.
  • The javacore's NATIVEMEMINFO attributes native memory by JVM component. Diff two javacores; don't read absolutes.
  • Capture evidence before the limit (guardian / alert automation), and put the javacore first.
  • Cap what can be capped (MaxDirectMemorySize, thread pools, MALLOC_ARENA_MAX). Measure the rest.

D · Forensics readiness: what must be in place to locate a native leak

Native leaks are where OpenJ9 shines: native-memory accounting (NATIVEMEMINFO) is in every javacore with no flag, and a javacore can be taken at any moment. The constraints are timing (two javacores from the same JVM, taken while there's still headroom) and the OS-level tooling you need once the growth turns out to be outside the JVM's own accounting.
